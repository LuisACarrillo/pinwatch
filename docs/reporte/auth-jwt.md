# Autenticación con JWT

## ¿Por qué JWT con Argon2id y la llave en Secrets Manager?

Antes, la API recibía el `user_id` en el body o en la query, así que cualquiera podía publicar, dar like o borrar tableros como si fuera otro usuario, y el cliente mandaba su propio `password_hash`. Ahora el usuario se registra e inicia sesión en `/auth`, y la API le entrega un JSON Web Token firmado con HS256. Elegimos JWT porque la API va a correr en AWS Lambda, que no guarda estado entre invocaciones: el token lleva dentro el id del usuario y su firma, así que cualquier instancia lo valida sin consultar una tabla de sesiones ni agregar un servicio como ElastiCache. La llave con que se firma es la misma `jwt_signing_key` que ya vive en Secrets Manager, no está en el código y la API la guarda en memoria cinco minutos. El token vence en 60 minutos y no hay refresh token; así, uno robado sirve poco tiempo y el diseño se mantiene simple para el alcance del proyecto. Al validar solo aceptamos el algoritmo configurado, lo que descarta tokens sin firma (`alg: none`). Las contraseñas se guardan con Argon2id, la primera recomendación de OWASP: el hash usa mucha memoria y eso encarece los ataques con GPU, y a diferencia de bcrypt no recorta las contraseñas a 72 bytes. Además, el login responde lo mismo, y en un tiempo parecido, cuando el email no existe y cuando la contraseña está mal, para no revelar qué cuentas existen. Las rutas que escriben toman el usuario del token, y en los tableros además se comprueba que quien los modifica sea su dueño.
